## TL;DR

A graph of agents is not an explanation of a system. The explanation starts with what must be accomplished (**Task**), what execution can observe and change (**Environment**), and how it acts (**Capacity**). An agent is the interaction process instantiated under those conditions. This view changes what counts as progress: a missing observation can look like weak reasoning; a better library can look like a better model; a new proof plan can look like parallel speedup; and a relaxed verifier can look like self-improvement. TEC turns these confounds into six propositions and a set of experiments. The central demand is simple: **identify which relation improved, instead of crediting the population of agents.**

---

## 1. Agent count is a poor explanation

Suppose a team proves a theorem that one agent failed to prove. What made the difference? Perhaps the team explored more candidates. Perhaps one member found a library theorem the original agent never saw. Perhaps the division of work exposed a missing assumption. Or perhaps the team submitted an easier statement, and the evaluator checked only that its file compiled. “Four agents beat one” distinguishes none of these explanations.

This is a practical problem in MAS evaluation. [Cemri et al. (2025)](https://arxiv.org/abs/2503.13657) developed a failure taxonomy from over 1,600 traces across seven systems, including specification, coordination and verification failures. [Kapoor et al. (2024)](https://arxiv.org/abs/2407.01502) showed why accuracy alone can obscure the value of simpler, cheaper agents. Practitioners also report different outcomes under different workloads: [Anthropic's research system](https://www.anthropic.com/engineering/multi-agent-research-system) benefits from parallel exploration, while [Cognition's account](https://cognition.ai/blog/dont-build-multi-agents) emphasizes the damage caused by fragmented context in software work. [E] The interesting question is which conditions produce each outcome.

Our usual nouns are too coarse for that question. “Critic” can mean a different prompt, a different obligation, a different view of the evidence, or authority to reject an answer. “Memory” can mean stored facts, retrieval, or a procedure that changes future reasoning. “Topology” can mean dependencies, communication, or control. Calling each of these a component does not tell us what an intervention changes.

TEC starts one level below these organizational forms. It describes the conditions that make an execution possible, then asks how familiar MAS mechanisms alter those conditions. The aim is to make competing explanations experimentally separable.

## 2. The spine: essence precedes existence

Sartre's paper-knife has a purpose and a method of manufacture before the particular object exists. This is his example of an artifact for which essence precedes existence, in contrast to his account of human existence (Sartre, 1946). An engineered agent belongs on the artifact side of that distinction: we specify a purpose, provide access to a world, and supply a means of acting before we launch its execution.

TEC gives that design three parts:

- **Task:** the outcome to pursue, with the scope needed to identify it.
- **Environment:** the state and interaction boundary through which execution observes and acts.
- **Capacity:** the reusable means of selecting and performing actions.

Binding these conditions produces an execution setup. **The agent is the running interaction process under that setup.** Its observations, actions and history develop over time; its next move is not a field in the specification. [D]

Self-modification fits this account without reversing a philosophical arrow. A run produces evidence; an update procedure uses that evidence to change a reusable configuration; later execution uses the changed configuration. A correction to the current proof changes the current state. Saving a new proof-search procedure changes how future runs act. **Self-improvement is the further claim that this change makes the system better at an objective that remains comparable.** Section 6.6 examines how that claim can fail even as internal scores rise.

## 3. One proof task, four execution units

Our running task is to prove that there are infinitely many primes congruent to 3 modulo 4. We state it in the form the final artifact must establish:

$$
\forall B\in\mathbb N,\quad \exists q\in\mathbb N:\quad q>B\;\land\;q\text{ is prime}\;\land\;q\equiv3\pmod4.
$$

This example has substantive intermediate results, a large formal library to search, and an exact distinction between checking a proof and checking the requested proof. It also has a useful shortcut: the fixed Mathlib version used as our reference contains [`Nat.forall_exists_prime_gt_and_modEq`](https://github.com/leanprover-community/mathlib4/blob/c5ea00351c28e24afc9f0f84379aa41082b1188f/Mathlib/NumberTheory/LSeries/PrimesInAP.lean#L504), which specializes to this goal. Successful retrieval can replace a constructive plan with an application of that theorem. That is a baseline the team must beat, and a concrete example of why a task has no unique execution plan.

### 3.1 Task: enough to identify success

The minimum Task consists of the requested outcome and its scope. Here the domain is the natural numbers, the bound B is arbitrary, and the result must supply a larger prime in the specified residue class. Returning q = 3 proves that one such prime exists; it does not prove the requested unboundedness. The distinction comes from the task itself.

For this execution, we additionally require a Lean proof of the fixed target under an agreed import and axiom policy. The verifier therefore has two jobs: check the proof term, and check that its type establishes the preserved target. A task can exist before an automated verifier is available. A claim of completion needs a justified way to decide whether that task was met.

The constructive plan uses two pieces that can be developed independently once their interfaces are fixed:

1. **Construction.** Let S be the finite set of primes at most B that are 3 modulo 4, and let P be their product. The empty product is 1, so P ≥ 1. Set N = 4P − 1. Then N ≥ 3 and N is 3 modulo 4. No member of S divides N: it divides 4P, and dividing both would force it to divide 1.
2. **Factor lemma.** Every natural number that is 3 modulo 4 has a prime divisor that is 3 modulo 4. Such a number is odd, so its prime factors, counted with multiplicity, are 1 or 3 modulo 4. If all were 1, their product would be 1 modulo 4, a contradiction.

Combining them gives a prime q dividing N in the required residue class. Since q cannot belong to S, it exceeds B. The factor lemma is reusable in later residue and prime-divisor arguments; its proof does not depend on this particular S or B. The same mathematical results have formal proofs in [_Mathematics in Lean_](https://github.com/leanprover-community/mathematics_in_lean/blob/dd6d752fedb14082f557913c2dccb2d4851e5173/MIL/C05_Elementary_Number_Theory/solutions/Solutions_S03_Infinitely_Many_Primes.lean#L164), whose infinitude proof uses a different construction. The factor lemma there is a declaration in the tutorial, not a claim about its native availability in Mathlib.

This decomposition explains why some management information becomes necessary:

- **A handoff contract** preserves the facts the next proof needs. Builder must deliver the residue condition as well as nondivisibility; a generic “candidate checked” is insufficient.
- **A dependency** records when an obligation can start. Factor can prove the general lemma before Builder finishes, but the final application needs both results.
- **Provenance** prevents approval of one theorem or revision from being attached to another. Store the declaration, exact type, source version and check result together when results cross a handoff or enter a shared library.
- **A budget and status** control execution: whether search should continue, and which obligations are ready. They help run the plan; they do not become additional mathematical constituents of the theorem.

Each addition answers a problem introduced by the execution design. None warrants a mandatory field in every conceivable Task.

### 3.2 Environment: available is different from observed

The Environment contains the pinned library sources and theorem index, definitions, per-agent working modules, shared declarations and compiler reports. Access rules determine which parts each execution can read or alter. The target and acceptance policy are preserved separately from the candidate files.

A **view** is the portion of this environment an agent can access. An **observation** is a result it actually receives, such as a theorem type returned by search. The **active context** is the input assembled for a particular model call. A library declaration can be accessible without being retrieved, and retrieved without surviving the next summary. These distinctions matter in a library far larger than one model input.

The same distinction applies to checking. A build report that says “success” is an observation about a submitted file. The exact declaration type is a different observation. An Auditor that receives the first and cannot obtain the second lacks evidence needed to determine whether the file proves our target.

### 3.3 Capacity and Agent: means of acting, then interaction

Capacity minimally supplies an action-selection procedure and the actions it can perform. Here a model with reusable instructions chooses searches and proof steps; tools let it inspect types, edit modules and request checks. The search operation belongs to Capacity; the indexed library it searches belongs to Environment. Which theorem comes back depends on both.

We keep four execution units throughout the article. They may share model weights while using different instructions and access. Each has a changing history; the table fixes its initial responsibility, not its trajectory.

| Agent          | Assigned task                                            | Capacity emphasis                                       | Default view                                                                   |
| -------------- | -------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **Integrator** | Fix interfaces; combine returned results into the target | Decomposition, type inspection, theorem application     | Original target, complete returned types, integration module and build reports |
| **Builder**    | Construct N and prove its required properties            | Finite-product arithmetic and local proof search        | S and its assumptions, arithmetic library search, its working module           |
| **Factor**     | Obtain the general residue-to-prime-factor lemma         | Factorization reasoning and theorem retrieval           | Factorization and residue search results, full types, its working module       |
| **Auditor**    | Decide whether the final artifact establishes the target | Target comparison, kernel checking and axiom inspection | Preserved target, final declaration and dependencies, pinned acceptance policy |

Access can be expanded by an explicit operation. Giving every unit a search interface still does not make every library theorem an observation in every run.

For example, Builder may initially reuse the familiar Euclid construction 4P + 1. A check then exposes the missing residue condition. Builder revises the candidate to 4P − 1 and proves the required properties. The task, model and tools can stay fixed across this sequence. The workspace and execution history change, and those changes affect the next action. **That evolving observation–action loop is the agent.** [D]

### 3.4 Five operators organize these executions

TEC names five organizational operations:

- **generate** states or refines obligations, including the two branches of the constructive proof.
- **match** selects a capacity with the access needed for an obligation.
- **assemble** selects observations and history for a model call.
- **verify** judges an artifact against an obligation, locally or at the root.
- **evolve** changes reusable capacity or configuration from execution evidence.

These operators need not be separate services or a single linear pipeline. Integrator can generate a replacement obligation after an unsuccessful check. Assembly recurs at each call. Evolve may propose a new retrieval procedure for future tasks; it is distinct from fixing the current proof.

## 4. Reinterpreting the objects of MAS research

TEC asks what a familiar research object changes in an execution. This makes topology, roles, communication, memory and workflow search comparable without pretending they are the same intervention.

### 4.1 Topology records a relation chosen by the designer

In the constructive plan, Integrator first fixes the interfaces. Builder and Factor then work independently. Integrator joins their outputs, and Auditor checks the result. Draw an edge whenever an obligation requires another's output. The resulting graph has **five obligation nodes and four agents**: Integrator owns both the first and the join node.

A serial variant makes Factor wait for Builder and solve the factor obligation for the particular N. The parallel variant asks Factor for the general lemma up front. This change in the assigned obligation removes a dependency; it is not accomplished merely by drawing a second branch.

Now hold the parallel graph fixed. One version delivers only statuses to Integrator; another supplies exact theorem types and assumptions. The graph is identical, but the information available for composition is different. A communication graph would record who can exchange messages; an authority graph would record who can assign work or accept results. Neither is necessarily this dependency graph.

This is what **projection** means: choose one relation from the complete execution design and retain its nodes and edges. The graph preserves that relation while leaving out other facts. It is a useful representation with a specified meaning, not an independent cause of performance. [D]

[GPTSwarm](https://arxiv.org/abs/2402.16823v3), for example, represents operations as nodes and optimizes prompts as well as connectivity. A node need not be an entire agent. TEC separates the changed action-selection setup from the changed information flow, so their joint benefit does not get assigned to graph shape alone.

### 4.2 Roles and hierarchy bundle obligations, instructions and authority

“Factor specialist” bundles an assigned lemma, instructions for finding or proving it, and access to relevant material. “Auditor” adds a decision right over acceptance. A role label specifies none of these by itself.

[MetaGPT](https://arxiv.org/abs/2308.00352v7) uses standard operating procedures and structured handoffs; [Magentic-One](https://arxiv.org/abs/2411.04468v1) gives an Orchestrator responsibility for planning, progress tracking and replanning. TEC reads these as allocations of **generate**, **match** and **verify**, supported by particular capacities and views. A hierarchy matters when it changes who can make these decisions or what evidence they receive.

If Integrator invokes Factor through a tool interface, the call is one Integrator action. Factor is still an execution unit with its own observations, searches and proof attempts. “Tool” names the calling interface; “agent” names the process behind it. This separates a hierarchy of calls from a claim that one role is intrinsically more capable.

### 4.3 Communication determines what survives a handoff

A communication mechanism writes information into an inbox, a shared module or another observable part of Environment. Assembly determines what reaches the recipient's next decision. Delivery, accessibility and inclusion in context are separate events.

For our team, a useful handoff from Factor preserves a statement of the form “for every n with n ≡ 3 modulo 4, there exists a prime divisor q with q ≡ 3 modulo 4.” Replacing it with “factor step verified” removes the premise Integrator must discharge. The message becomes cheaper to send while the integration problem becomes harder to solve.

Structured outputs, shared workspaces and message routing therefore deserve evaluation at the level of retained obligations and evidence. A message-count comparison misses this difference. The same content can also have different delivery and synchronization costs across implementations; those costs belong in the execution record.

### 4.4 Memory changes what later executions can use

[MemGPT](https://arxiv.org/abs/2310.08560v2) manages movement between stored information and model context. [A-MEM](https://arxiv.org/abs/2502.12110v11) organizes and links retained notes. [Agent Workflow Memory](https://arxiv.org/abs/2409.07429v1) derives reusable workflows from earlier activity. These research objects cross different TEC boundaries:

- Saving Factor's checked lemma, complete type and source version changes **Environment**.
- Making that lemma discoverable under a later residue obligation changes retrieval and **assemble**.
- Loading a reusable procedure that searches for a matching declaration before deriving it changes **Capacity**.

This classification is functional. A workflow can be stored as data and later loaded as a procedure; its filename does not settle its role. The corresponding experiments differ: retain the store but disable retrieval, preserve retrieval but remove the useful lemma, or change the procedure while holding both fixed.

The distinction has a substantive consequence. One agent can contribute a lemma that reduces another agent's future work without either model changing. The gain belongs to shared accumulation. Section 6.4 asks what happens when the same mechanism also distributes mistakes.

### 4.5 Automatic design searches choices, not an indivisible “agent”

[DSPy](https://arxiv.org/abs/2310.03714v1) optimizes components of language-model programs; [ADAS](https://arxiv.org/abs/2408.08435v2) searches agent code; [AFlow](https://arxiv.org/abs/2410.10762v3) searches executable workflows. These search spaces can change prompts, control flow, tool use and information routing in different combinations.

In our scene, a candidate could give Factor better retrieval instructions, change its library view, or replace the constructive plan with direct theorem application. These are different interventions even if each is saved as one program. TEC describes the candidate by the relationships it changes; **evolve** adopts reusable changes after evaluation. Section 6.5 explains why the search must sometimes retain a change whose value appears only alongside another component.

## 5. Where TEC sits among earlier ideas

Simon gives the philosophical connection a design interpretation. In _The Sciences of the Artificial_, an artifact's behavior depends on its purpose, its internal organization and the external conditions in which it operates. Its design joins an inner and an outer environment. These correspond closely to Task, Capacity and Environment in TEC ([Simon, 1996, pp. 5–6](https://andymatuschak.org/files/papers/Simon%20-%201996%20-%20The%20Sciences%20of%20the%20Artificial.pdf); first edition 1969). Sartre locates the artifact in relation to its design; Simon explains why that design must be understood in relation to a purpose and a world.

The connection to earlier technical fields is equally specific. LLM agents make instructions, context selection and the creation of new execution units unusually easy to vary. **This enlarges the design space while leaving computation, access and coordination costly.** The useful question is which variables each field teaches us to keep separate.

### 5.1 Distributed AI: suitability belongs to a worker in a situation

The contract net addresses allocation when participants hold information the coordinator lacks. A manager announces an obligation, potential contractors assess their suitability, and the manager chooses from their replies. This was already about capabilities and local information, not simply who was idle ([Smith, 1980](https://www.reidgsmith.com/The_Contract_Net_Protocol_Dec-1980.pdf)). Blackboard systems organize contributions around a shared evolving problem state, with a control mechanism deciding which applicable contribution to run ([Erman et al., 1980](https://mas.cs.umass.edu/Documents/Erman_Hearsay80.pdf)).

For an LLM team, launching another copy of the model supplies another execution, but does not automatically supply a useful theorem, search procedure or view. Factor's suitability depends on both its capacity to retrieve and apply declarations and its access to a relevant library. That makes **the capacity–environment pair the object of matching**. A leaderboard score for the model alone leaves out part of the allocation problem. P5 turns this dependence into a concrete failure mode of component-wise optimization.

### 5.2 Organization theory: moving information is part of doing the work

Coordination theory distinguishes dependencies such as producer–consumer relations, shared resources and the reconciliation of contributions ([Malone and Crowston, 1994](https://crowston.syr.edu/sites/default/files/acmcs94.pdf)). Galbraith's information-processing account explains why uncertain work requires information exchange that cannot all be prescribed in advance ([Galbraith, 1974](https://jaygalbraith.com/wp-content/uploads/2024/03/infoprocess1974.pdf)).

An LLM system makes one part of this cost unusually concrete: a retained result must compete for finite model input before it can influence a decision. Context carries selected evidence and recalled history while consuming inference resources. Keeping a theorem in storage and putting its useful type into Integrator's current input are different organizational achievements.

This links P1 and P4. Discarding a premise to save context can make the current task undecidable from the available evidence. Retaining and retrieving a checked premise can eliminate future work. The design problem is to preserve the distinctions future decisions need at an acceptable cost. An archive's size is a poor substitute for that measurement.

### 5.3 Ensembles: answer diversity and evidence diversity are different resources

Ensemble analysis relates combined error to individual errors, their dependence and the combining rule. Under squared loss, the familiar ambiguity decomposition quantifies the benefit of disagreement among numerical predictors ([Krogh and Vedelsby, 1995](https://proceedings.neurips.cc/paper_files/paper/1994/file/b8c37e33defde51cf91e1e03e51657da-Paper.pdf)). A proof system needs a different combining rule, but it still needs this separation of mechanisms.

Same-weight instances can disagree: stochastic sampling from one model produces different reasoning paths, as self-consistency demonstrates ([Wang et al., 2023](https://arxiv.org/abs/2203.11171)). More candidates can improve the chance of finding a correct proof. They do not reveal which theorem a hidden build artifact actually declares. Repeated sampling changes the distribution of explored answers; obtaining the declaration changes the evidence on which an answer can depend.

TEC therefore separates changes to Capacity, observations supplied by **assemble**, and the selection or composition performed by **verify** and Integrator. P1 bounds the second resource; P2 examines what the combining procedure must establish. Neither requires independently trained models, and neither follows from agent count alone.

### 5.4 Evolutionary computation: search needs a reference for what survives

Evolutionary methods distinguish producing candidates, evaluating them and retaining useful alternatives. MAP-Elites preserves high-quality candidates across chosen behavioral categories instead of keeping only one overall winner ([Mouret and Clune, 2015](https://arxiv.org/abs/1504.04909)). For agent design, an archive can retain a retrieval-heavy capacity and a derivation-heavy capacity for different library conditions. That is a mechanism for preserving alternatives that **match** may later exploit.

Evaluation can also change during search; this is not an LLM novelty. Hillis coevolved sorting networks and test cases while retaining the external objective of correct sorting ([Hillis, 1990](https://www.cse.unr.edu/~sushil/class/gas/papers/DannyHillisCoevolution.pdf)). What editable agent harnesses make convenient is changing the candidate, its task generator and its evaluator in the same medium, sometimes through the same execution.

The TEC question is therefore about authority: which of **generate**, **verify** and **evolve** can the candidate alter, and what remains outside that authority to assess improvement? P6 measures the resulting gap between internal claims and a preserved objective. This puts self-modification in an existing tradition while identifying the boundary an agent evaluation must expose.

## 6. Six propositions about improvement

The propositions form a connected account of execution. P1 concerns evidence. P2 and P3 concern a plan's logical and temporal dependencies. P4 connects reusable results to both: their contracts must remain valid, and their use changes future plans. P5 concerns the joint feasibility of an environment and a capacity. P6 asks whether the criterion used to accept these improvements still measures the intended task.

### 6.1 P1 — An evidence bottleneck can masquerade as a capability limit

Consider two build artifacts. One proves our unbounded-prime target; the other proves only that there exists a prime congruent to 3 modulo 4. Both files compile. A wrapper that reports only “Lean: success” gives Auditor the same observation for results that require different acceptance decisions. A familiar automation shortcut has removed the exact distinction the task requires.

The information bound is precise. Fix the team's capacities, policies and joint prior information, including private memories. Suppose the two cases induce the same initial information and, after every possible visible history, every permitted action has the same conditional observation distribution. Their distributions over final decisions must then also be identical: at each step, the same available information produces the same distribution of actions and subsequent observations. For a balanced pair requiring opposite binary verdicts, average accuracy is at most one half. [D]

Retrieving the declaration breaks this premise and can solve the problem. More debate over the build status cannot. The relevant unit is the **joint evidence available to the team**, not whether its members have different role names. More computation may extract implications from evidence already present; it cannot correlate a verdict with a hidden difference that no allowed observation exposes.

This gives a testable diagnostic: **how much reported “model failure” is actually a missing observation?** Take held-out failures labeled as verification problems in a trace corpus such as MAST, preserve the model and candidate, and restore task-relevant evidence omitted by the original context policy. Compare against both the original input and an equal-token irrelevant addition, with matched budgets. Measure the fraction repaired and the change in false acceptance. The prediction is that evidence restoration repairs a meaningful subset without a model upgrade. [C] Cemri et al. supply a taxonomy and traces; they do not establish this counterfactual repair rate.

### 6.2 P2 — Every decomposition incurs a composition obligation

Builder can return a locally correct result that does not meet Factor's needs. Suppose its assigned contract asks only for a number divisible by no member of S. Reusing the ordinary Euclid pattern, Builder returns N = 4P + 1 and proves that nondivisibility claim. Factor separately proves the correct lemma conditional on N being 3 modulo 4. Both local checks pass. Their results do not compose.

The mismatch is numerical as well as logical. For S = \{3, 7\}, P = 21. Builder's candidate is 85 = 5 × 17; neither 3 nor 7 divides it, but both its prime factors are 1 modulo 4. The intended candidate is 83 = 4P − 1. If Builder's contract already requires N ≡ 3 modulo 4, the wrong construction fails locally. It slips through only when decomposition omitted that obligation or a handoff concealed it.

**Sound local verification guarantees the parent only when a sound composition rule connects the local contracts to the parent goal.** [D] The reasoning has not disappeared through delegation. Part of it has moved into choosing interfaces, preserving assumptions and applying returned results. Lean's kernel will reject the unsupported final application; “all children passed” cannot substitute for that check.

An experiment can hold local theorem validity at 100% while progressively removing necessary type and hypothesis information from the summaries given to Integrator. Measure parent completion, repair calls and cost under a fixed budget. The prediction is that losing essential interface information damages integration even though the child success metric stays perfect. [C] Removing irrelevant text need not hurt. The causal variable is lost obligations, not compression as such.

### 6.3 P3 — The critical path belongs to a plan, not to the theorem

For a fixed acyclic plan D of serial operations, with fixed durations and p identical workers,

$$
\tau(D,p)\geq\max\left(\frac{W_D}{p},L_D\right),
$$

where W is total work and L is the longest dependency path. Relative to executing that same work on one worker, speedup cannot exceed the smaller of p and W/L. [D]

In our constructive plan, Factor can establish its general lemma while Builder constructs N. Integrator must wait for both, and Auditor must wait for integration. More workers eventually leave those dependencies unchanged. But retrieving the existing Mathlib theorem removes both branches and most of the integration work. The Task stays fixed while the feasible plan changes through Environment and Capacity.

_Figure 5. Vary workers within a plan, then switch plans. The constructive example uses normalized operation costs 1, 2, 4, 1, 1; direct lookup uses 2 and 1. The display keeps total work separate from scheduling speedup._

This supplies a diagnostic for scaling claims. Freeze the plan and operation costs: speedup must respect W/L. A reported violation means at least one comparison assumption changed. Replanning is one explanation; changed work, caching, per-operation speed or an inefficient serial baseline are others. The trace must identify which. A speedup above the worker count cannot come solely from scheduling the same fixed-cost operations.

The stronger research question is consequently **which capacities and environments make better plans discoverable?** In this example, library search can matter more than another worker. A scaling study that silently permits new retrieval or decomposition measures plan discovery together with parallel execution.

### 6.4 P4 — Shared accumulation amplifies the admission policy

Once Factor's lemma is stored with a checked proof, its full type and version, another proof task can reuse it. If retrieval and application cost less than derivation, that obligation requires less work with every individual Capacity held fixed. [D] The benefit passes through **verify → retain → retrieve → revise the plan**. It belongs to the system's accumulated Environment.

The same path also distributes mistakes. A theorem can be valid while its index entry advertises a stronger claim, drops a hypothesis or points to another revision. A formal store that rechecks exact types prevents those mistakes from becoming accepted proofs. A store admitted through summaries or a fallible review procedure can pass them downstream. Verification at the library boundary therefore determines what accumulation amplifies.

Let q be the probability that an accepted, selected artifact fails its advertised contract. This is not the verifier's false-positive rate α. If candidate invalidity has prevalence π and valid candidates are accepted with probability β, then

$$
q=\frac{\pi\alpha}{\pi\alpha+(1-\pi)\beta}.
$$

This expression assumes selected entries follow the accepted population; biased retrieval changes the relevant q. If a later plan relies without further checking on k distinct, independently contaminated necessary artifacts, the probability all those contracts are valid is

$$
P_{\mathrm{clean}}=(1-q)^k.
$$

At q = 1%, that probability is about 90% for ten dependencies and 61% for fifty. This is a conditional contamination calculation, not an observed agent failure curve. Reusing the same bad lemma creates correlated exposure; repeated uses cannot be counted as independent draws. Downstream checking can turn contamination into rejection and repair rather than a false accepted proof.

**Useful accumulation is limited by the quality of what enters the store and the number of dependencies later work entrusts to it.** [D] Growing a library that nobody uses creates no such exposure. Nor does α alone imply a universal agent-count threshold. A useful experiment fixes admission quality and increases contribution rate, measuring actual reuse, contaminated dependency exposure, repair cost and accepted root proofs. The prediction is that increasing exposure can erase the gains from saved derivations, while exact-contract rechecking shifts the loss toward repair cost. [C] That is a stronger target for a shared proof commons than maximizing the number of stored lemmas.

### 6.5 P5 — A useful pair can be invisible to one-component search

A typed lemma library helps a capacity that can search and apply its declarations. A search-and-application procedure helps when relevant declarations are available. On proof tasks where neither derivation nor another retrieval route succeeds within the budget, adding only one may leave success unchanged while adding both improves it.

Write Sᵢⱼ for performance with Capacity version i and Environment version j. The pattern

$$
S_{00}=S_{10}=S_{01}<S_{11}
$$

is enough to defeat a search that changes one component at a time and retains only immediate improvements. Both first steps are rejected. A policy permitting neutral steps, joint edits or retained alternatives can reach the pair. Thus optimizing each component in isolation has no general guarantee of discovering their joint value. [D]

The corresponding experiment is a 2 × 2 comparison: base or search-capable Capacity crossed with absent or available typed library, with comparable budgets and the library's construction cost reported. Measure the interaction

$$
\Delta=S_{11}-S_{10}-S_{01}+S_{00}
$$

on the chosen performance scale. Then plant such a pair in an agent-design search space and test whether the actual proposal and retention policy finds it. ADAS and AFlow can search richer edits; they should not be labeled incapable merely because a constrained greedy policy fails. The empirical question is which search mechanisms preserve enough combinations to discover the planted interaction. [C]

This also changes matching: the relevant evidence is performance of a Capacity in a specified Environment. A capacity ranking can reverse when library access or representation changes.

### 6.6 P6 — A self-modifying system needs a score it cannot redefine

Our proof task exposes the problem with two short declarations. One establishes “there exists a prime that is 3 modulo 4,” using 3 as a witness. The other takes the entire requested theorem as an assumption and returns it. Both can compile without an unproved placeholder. Neither discharges the original task.

These are executable checks, not hypothetical kernel failures. With Lean 4.25 and `Std`, the [weakened and conditional declarations](/assets/img/blog/tec-essence-precedes-existence/proof-checks/PrimeAudit.lean) compile; submitting them to the [preserved full target](/assets/img/blog/tec-essence-precedes-existence/proof-checks/RejectedTarget.lean) produces type errors. The [run instructions and captured output](/assets/img/blog/tec-essence-precedes-existence/proof-checks/README.md) record the scope and results. The checks use a small local prime definition and do not execute the full Mathlib infinitude proof. Lean checks proof terms against their declared types; [target and axiom inspection](https://lean-lang.org/doc/reference/4.34.0-rc2/ValidatingProofs/) are part of establishing what was actually proved.

Now let a self-modifying system edit its local task generator or acceptance wrapper. Replacing the root goal with the weaker one can raise its reported success rate. If evaluation reads that report, the system has changed the meaning of its score. **A score increase identifies improvement only relative to a success criterion preserved across the comparison.** [D]

We can measure the discrepancy. Score outputs from old and new system versions on the same held-out tasks, using both their internal assessment and a fixed external assessment, with aligned scales and weights. Define

$$
\delta=(S_{\mathrm{in,new}}-S_{\mathrm{in,old}})
       -(S_{\mathrm{ext,new}}-S_{\mathrm{ext,old}}).
$$

A positive δ means the internally reported gain exceeds the externally measured gain. Zero and negative values are possible. The gap measures divergence in claimed progress; by itself it does not identify intentional gaming or a verifier change. To isolate verifier drift, also cross-score a fixed collection of the same artifacts with the old, new and external verifiers. That removes changes in the artifact mix from the comparison.

The [Darwin Gödel Machine](https://arxiv.org/abs/2505.22954v2) evaluates agent revisions against external benchmarks and examines transfer to held-out settings. This supplies a reference beyond an agent's own completion reports. [E] Its evidence is therefore stronger than persistence or self-editing alone. Attribution still requires component controls: a better library, a better retrieval policy and a better reasoning procedure are different explanations for the same external gain.

## 7. What this account does not determine

TEC is a vocabulary for specifying interventions plus conditional propositions about their consequences. It is not a predictor of the best team size for an arbitrary task. Scheduling needs operation costs; accumulation needs reuse and admission statistics; matching needs evidence about particular capacity–environment pairs. The empirical value of the framework depends on whether measuring these quantities explains failures and improves design decisions better than coarser descriptions do.

Its account of purpose also describes the designer's assignment, not a guarantee of agent obedience. Deceptive reports, conflicting objectives and adversarial inputs require models of incentives and trust beyond the cooperative proof setting. A pinned target is an evaluation boundary; it does not ensure that every participant pursues it.

Finally, the boundary between run state and reusable configuration must be recorded when it changes. A system that edits its instructions mid-run can be described as a sequence of configurations and interactions. Its initial triple alone is insufficient to reconstruct the whole execution. Weight updates fit under Capacity changes too, but their dynamics and interference require additional learning theory.

## 8. Experiments that could change the argument

### 8.1 Start with the cheapest discriminating tests

The logical bounds follow from their premises. Experiments test whether those premises describe consequential failures in actual systems, and whether TEC's proposed interventions help. The following order is an approximate implementation-cost order, from small artifact checks to repeated multi-task runs.

| Cost        | Test                                                                                                                                 | What to measure                                                                            | What would weaken the TEC explanation?                                                                                                 |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| Lowest      | **Target audit — P1, P6.** Cross-check compiled artifacts against preserved theorem types; run the linked Lean probes.               | False acceptance by status-only versus exact-target wrappers; internal/external score gap. | Existing wrappers already preserve and check the target in the relevant failures, leaving no target-loss explanation.                  |
| Low         | **Composition — P2.** Use the 85 counterexample; keep child statements valid while removing essential handoff information.           | Root completion and repair cost at fixed child validity and budget.                        | Integrator reliably reconstructs the missing interface at negligible cost across the tested tasks.                                     |
| Low–medium  | **Plan and schedule — P3.** Replay a fixed operation DAG at different worker counts; separately allow theorem lookup and replanning. | Work, span, operation times, retrieval cost and latency.                                   | The apparent extra scaling is explained by baseline or operation-cost changes, with no contribution from discovering a different plan. |
| Medium      | **Planted complements — P5.** Cross two capacities with two library conditions, then test search policies.                           | Interaction Δ, pair-discovery rate and total search cost.                                  | No positive interaction remains under matched resources, or restricted search reaches the pair through other effective steps.          |
| Medium–high | **Evidence restoration — P1.** Revisit held-out verification failures with the same model and candidate.                             | Repair rate and false acceptance against original and equal-token control contexts.        | Relevant evidence was already accessible and used, or restoring it performs no better than the controls.                               |
| Highest     | **Shared accumulation — P4.** Freeze capacities; vary store admission quality and contribution rate across related proof tasks.      | Net work saved, reused dependencies, contamination, repair and final accepted proofs.      | Stored contamination rarely reaches later obligations, or its measured cost is negligible compared with reuse gains in this regime.    |

The [composition check](/assets/img/blog/tec-essence-precedes-existence/proof-checks/Composition.lean) and target probes are executed demonstrations. The larger experiments above are a research agenda, not results claimed by this article.

### 8.2 Keep the comparison interpretable

Each experiment needs a budget-matched single-agent or repeated-sampling baseline. Several instances of the same model with the same inputs may buy useful candidate diversity; that benefit should be measured before it is credited to organization. A synthesizing Integrator does additional work beyond selecting a candidate, and its cost belongs in the comparison.

For configuration updates, retain the old version and record what later runs actually load. Compare on tasks that did not guide generation or selection of the update, measure both success and total cost, and revisit earlier successes for regressions. If Environment and Capacity changed together, cross their versions where feasible. If the evaluator changed, cross-score artifacts as in P6. These controls distinguish a useful whole-system improvement from an unsupported explanation of why it occurred.

## 9. What should count as progress

The proof team makes three failures of interpretation concrete. A compiler-success message can conceal a changed target. A retrieved theorem can remove work that extra workers could only schedule. A shared lemma can improve every later execution without changing any model.

These are different routes to a higher score, and they require different evidence. Treating them all as “more capable agents” conceals the design decision worth keeping.

An agent's essence precedes its existence: a purpose, an interaction boundary and a means of acting make the run possible. The run then produces a history that can inform the next design. The research task is to explain which changes in that design preserve evidence, support composition, reduce work and improve performance on an objective that still means the same thing.
