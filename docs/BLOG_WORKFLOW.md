# Blog 协作、审核与发布流程

本文适用于本项目中所有 Blog 的策划、起草、改写、配图、翻译、审核与发布。它记录作者与 Agent 的长期合作方式；每篇文章的具体决定仍以该文章的 Article Contract 为单一事实源。Contract 优先放在已有 GitHub Issue，没有 Issue 时使用作者指定的本地文件。

最新的作者指令优先于本文。一次文章的标题、篇幅、示例或配图决定不能自动套用到另一篇文章；先把它记录进当前 Article Contract。

纯粹把 Markdown Vault 中已经完成的文章同步到网站时，执行 `AGENTS.md` 的 `Markdown Vault Sync`，不需要重新建立 Article Contract。同步任务一旦包含实质性改写、新论证、翻译或配图，则相关部分同时执行本文流程。

## 一、作者的长期要求

每篇文章都应满足以下要求：

- **深入浅出**：先让第一次接触主题的读者建立正确心智模型，再进入实现细节。不能把读者理解文章所必需的背景留给外部链接。
- **中心明确**：一篇文章回答一个核心问题。先写出直接答案，再决定章节；不要为了展示资料量而同时承担多个后续篇目的任务。
- **完整成文**：交付物是可以独立阅读的 Blog，而不是资料清单、源码导览、概念提纲或“请参考官方教程”。
- **开头直接**：从具体矛盾、可观察行为或读者真正会问的问题切入，在首屏定义核心对象。类比只能在对象和机制已经落地以后辅助理解。
- **示例明显**：示例必须让边界一眼可见。读者看不懂时，换成更直接的例子；不要靠增加抽象解释挽救一个不合适的例子。
- **术语稳定**：Article Contract 中确认保留英文的术语，在标题、正文、图注和双语版本中保持一致。当前 DeepSeek Harness 系列保留 `Cordis`、`Plugin`、`Tool`、`Context`、`Service`、`inject`、`Effect` 等系统术语。
- **证据进入正文**：官方文档中的好教程要在正文中完整解释。链接用于证明来源和方便延伸阅读，不能替正文承担关键推理。
- **范围克制**：本篇只讲清自己的中心判断。与后续文章重叠的内容只讲到当前推理所需的程度，并明确交给哪一篇继续。
- **文本分层**：Blog 正文只推进读者对主题的理解。写作取舍、章节安排理由、审核状态和给作者的解释属于协作对话或 Article Contract，不能混进正文。
- **复读后交付**：每次完成新稿或实质性改写后，必须由另一个 Agent 以首次读者身份完整复读。内部复读通过前，不交给作者审核，也不发布；复读通过不等于获得发布授权。

讨论需求时，每次最多集中询问五个问题。收到回答后，先更新 Article Contract，再继续下一组；避免一次抛出过长问卷。

## 二、严格区分协作文本与 Blog 正文

写任何段落前，先判断它的接收者：

| 接收者            | 应该包含什么                                             | 存放位置                      |
| ----------------- | -------------------------------------------------------- | ----------------------------- |
| Blog 读者         | 主题定义、机制、证据、例子、推论、限制和必要的阅读导航   | `src/content/posts/*.md`      |
| 作者              | 为什么这样组织、为什么换例子、有哪些取舍、等待确认的决定 | 对话中的回复                  |
| 后续 Agent / 项目 | Article Contract、资料版本、审核结论、发布状态和后续分工 | tracking Issue 或作者指定文件 |

一句话是否属于正文，用下面的测试判断：**如果不考虑“我们正在写一篇文章”这件事，这句话是否仍在解释主题？** 如果答案是否定的，就把它移到给作者的回复或 Article Contract。

以下内容属于编辑说明，不能进入 Blog：

- “这个例子足够短，正文可以把它完整讲明白，无需让读者跳到链接里自己拼出结论。”
- “到这里再使用微服务类比，才不会把 Cordis 讲偏。”
- “本文接下来先讲……”“现在已经有足够背景……”“本篇讲到这里就够了。”
- 为什么选择某个标题、顺序、类比、图或引用方式；
- 本轮改了什么、哪些内容获得确认、准备怎样审核或发布。

把它们改成直接面向主题的句子。例如：

- 编辑说明：“这个例子足够短，正文可以完整讲明白。”
- Blog 正文：“`greet` 把 Plugin 的依赖声明、Tool 定义和 Registry 调用放在同一段代码里。”
- 编辑说明：“到这里再使用微服务类比。”
- Blog 正文：“Cordis 与微服务共享 provider/consumer 分离这一局部结构，但前者没有网络边界。”

必要的阅读导航可以保留，例如“先看一次启动过程，再解释各个角色”，前提是它帮助读者理解主题顺序，而不是向作者说明写作策略。最终审核必须逐句搜索 `本文`、`本篇`、`正文`、`读者无需`、`到这里`、`下面将` 等信号词；逐条判断，而不是机械删除。

## 三、每篇文章先建立 Article Contract

优先使用作者提供或项目中已有的 GitHub Issue。没有现成 Issue 时，不自动创建外部事项；先请作者确认新建 Issue，或把 Article Contract 写进作者指定的本地文件。起草前，Contract 至少记录以下内容；独立文章在 `Series position` 和 `Handoff` 中写明不属于系列：

| 字段            | 必须回答的问题                                           |
| --------------- | -------------------------------------------------------- |
| Series position | 这是系列第几篇？前后篇各自负责什么？                     |
| Reader          | 默认读者已经知道什么？哪些概念必须从零解释？             |
| Center question | 读完文章后，读者应能回答哪一个问题？                     |
| Direct answer   | 不借助类比，用一到三句话直接回答中心问题。               |
| Scope           | 本篇必须讲清哪些机制、例子和后果？                       |
| Non-scope       | 哪些内容明确交给后续文章或其他文档？                     |
| Terms           | 哪些术语保留英文？哪些中文表达已经获得作者确认？         |
| Evidence        | 使用哪个固定版本？哪些主张由哪些官方文档或源码支持？     |
| Examples        | 哪个最小例子负责教学？哪个真实系统例子只负责验证？       |
| Visual plan     | 需要几张图？每张图回答什么问题？最终图使用什么制作方式？ |
| Languages       | 只写一种语言还是双语？哪一版先写？翻译采用什么方式？     |
| Review mode     | 作者审核本地草稿，还是在内部审核通过后直接上线检查？     |
| Handoff         | 结尾把哪个未展开问题交给哪一篇文章或 Issue？             |

只有作者明确表示“可以起草”或给出等价授权后，才进入正文写作。若讨论中出现新的中心判断、范围或术语决定，先更新 Article Contract；使用 GitHub Issue 时同步更新其中的 `Current Consensus`。

## 四、证据与研究

1. 系列文章先读系列总控 Issue、当前 Article Contract、上一篇已发布文章，以及负责相邻主题的后续 Issue；独立文章只读取与当前主题直接相关的记录。
2. 对仍在快速变化的软件固定 commit、版本和核验日期。正文引用固定版本链接，避免文章内容与浮动文档互相漂移；不适用时在 Contract 中标为 `N/A` 并说明原因。
3. 技术或资料型文章的事实主张优先使用官方文档、类型定义、测试和实现源码。每个关键机制都应能对应到一项一手证据；个人反思与观点要清楚标成作者判断。
4. 技术或资料型文章建立简短的 claim-to-source map，至少覆盖中心定义、运行顺序、边界、失败或清理行为，以及真实例子；不适用时在 Contract 中标为 `N/A`。
5. 官方文档与源码表达不完全一致时，继续检查实现和测试；正文明确区分“开发者看到的接口”与“框架内部实际挂载的对象”。
6. 外部链接只承担出处和延伸阅读。读者不打开链接，也应能跟完整篇文章的主线。

技术或资料型文章证据充分的完成标准是：需要外部验证的中心判断、关键时序、概念边界和限制条件都有一手来源；正文没有把推理缺口藏在“参考文档”后面。

## 五、先设计解释顺序，再写章节

技术文章优先采用以下解释阶梯；可以调整，但不能跳过读者所需的台阶：

1. **Concrete tension**：展示一个反直觉事实、失败现象或具体问题。
2. **Direct definition**：直接回答核心对象是什么、由谁拥有、解决什么问题。
3. **Observable path**：用一次启动、调用、状态变化或最小代码路径说明它怎样运行。
4. **Concepts in place**：此时再引入组成概念、角色和约束。
5. **Complete teaching example**：用足够简单的例子把边界完整走一遍。
6. **Production confirmation**：用真实系统片段证明最小模型不是玩具，但不借机展开下一篇文章。
7. **Consequences and limits**：说明设计带来的好处、成本和不保证什么。
8. **Handoff**：重申本篇答案，并把剩余问题交给明确的后续文章。

类比属于第四步之后的解释工具，不是定义。作者在讨论中提出“像某种架构”时，应把它视为待校准的观察：先写清本体，再说明相似点和失效边界。不要把这句观察直接提升为标题、首段或中心判断。

章节标题应能单独通过 skim test：顺序读标题时，可以看到问题怎样一步步得到回答。概念名词列表不能代替运行过程。

## 六、示例与官方教程

- 教学例子只承担一个主要边界，输入、执行和结果应当明显。
- 如果官方教程已经提供合适的最小例子，在正文中给出完成理解所需的代码和逐步解释；链接放在例子开头作为来源。
- 从外向内解释代码：先说整个文件或模块是什么，再说激活入口、注册对象、运行时调用和结果回流。
- 明确区分“注册时发生什么”和“真正执行时发生什么”，以及“框架管理的对象”和“模型能看到的对象”。
- 真实生产例子放在教学例子之后，只验证同一结构确实被系统采用。不要让复杂实现反过来定义基础概念。
- 读者反馈“没看懂例子”时，优先替换例子或补齐缺失步骤；不要只增加总结句。

## 七、配图流程

每张图先在 Article Contract 中写清三个字段：`claim`、`visual job`、`reading`。

- `claim`：图前正文刚刚提出的主张。
- `visual job`：这张图让哪组关系、边界或时序比文字更容易看懂。
- `reading`：图后正文告诉读者应该从图中得到什么。

先审核关系，再制作最终图片。逻辑草图可以使用 Mermaid；当作者要求 ImageGen 时，最终发布图必须通过 ImageGen 生成，不能用 Mermaid、手写 SVG 或普通流程图替代。生成后必须检查：

- 组件的包含、并列和调用关系是否正确；
- 箭头方向、阶段先后和标签是否与正文一致；
- 桌面和移动端缩放后文字是否仍可读；
- 中英文 alt text 与图注是否各自自然；
- 图是否真正推进论证，而不只是装饰页面。

图片数量和风格以当前 Article Contract 为准。复用图片时，两种语言可以共用资产，但必须使用本地化 alt text 和图注。

## 八、双语起草

双语文章采用 Article Contract 中确认的母稿顺序。当前系列默认先完成英文论证，再根据同一论证自然重写中文；中文不是逐句翻译，必须符合中文阅读节奏，同时保持代码、事实、术语和章节职责一致。

每个版本都必须包含：

- frontmatter 中用于列表和搜索的 `overview`；
- 正文开头可见的 TLDR；
- 适用时包含相同的固定版本说明和证据边界；
- 对应的图、alt text、图注和延伸阅读；
- 相同的中心判断与 Article Contract 范围。

完成母稿后再写第二语言，避免两个未定稿版本同时漂移。修改中心结构时同步改两种语言；只修改语言节奏时不必机械保持句子数量一致。

## 九、独立 Agent 复读门槛

每次新稿或实质性改写完成并格式化后，派另一个 Agent 完整通读。复读 Agent 不直接编辑文件，以免作者失去对具体修改的可见性。

复读任务至少要求检查：

1. 第一次接触主题的读者会在哪个具体句子或段落卡住？
2. 首屏是否直接定义核心对象，并回答标题提出的问题？
3. 启动、调用或状态变化是否有缺失台阶？
4. 术语、provider/consumer、所有权和生命周期边界是否一致？
5. 示例是否完整区分相邻概念？
6. 类比是否后置，并明确写出失效边界？
7. 正文是否把必要解释外包给链接？
8. 正文是否混入本应写给作者或 Article Contract 的编辑说明、写作理由或审核状态？
9. DSH 或其他应用案例是否抢走文章主线？
10. 是否存在事实错误或超出证据范围的主张？
11. 给出明确结论：`内部复读通过 yes/no`。

若结论为 `no`，主 Agent 修正所有阻断项，再把完整新版本交回复读。只要修订改变了实质内容，就再次复读；直到另一 Agent 明确回答“无阻断问题，内部复读通过”。把最终结论记录到 Article Contract。

内部复读只判断文章质量，不决定下一步权限。通过以后，主 Agent 按 `Review mode` 执行：草稿审核模式的结论是“可交作者审核”，线上审核模式在发布条件全部满足后才是“可发布”。

## 十、作者审核与发布模式

Article Contract 必须记录当前审核模式：

### 草稿审核

适用于作者要求“先写，然后找我审核”的任务。完成内部复读和本地验证后：

- 展示修改文件和核心结构；
- 不提交、不推送、不更新线上文章；
- 等作者逐项确认或提出修改；
- 修改完成后重新走独立 Agent 复读。

### 线上审核

当前 DeepSeek Harness Blog 系列已获得“内部审核通过后直接推送网站，由作者线上检查”的授权。该授权只覆盖文章及其已确认资产，不覆盖无关代码或其他内容。

发布前必须满足：

- Article Contract 已确认；
- 另一 Agent 明确给出 `内部复读通过 yes`；
- Article Contract 要求的语言版本均已同步；
- 当前环境若提供写作 lint，则运行并记录实际命令；Prettier、`git diff --check` 和 `yarn build` 均通过；
- 只 stage 当前文章和已确认资产。

推送 `main` 后，等待 GitHub Pages 与 CI 成功，再检查线上页面。至少验证：

- 中英文 URL 返回正常；
- 新开头、关键标题和核心示例已经出现；
- 被替换的旧判断或旧段落已经消失；
- 图片可加载且关系正确；
- tracking Issue 或 Article Contract 已记录 commit、Pages run、CI run 和线上链接。

如果文章使用 tracking Issue，Issue 保持开启，直到作者明确完成线上审核。作者后续要求改回草稿审核时，以最新指令为准。

## 十一、处理作者反馈

作者说“没看懂”时，把它当作解释结构失败的证据，不把责任归给读者。先判断属于哪一类：

- **定义缺失**：读者还不知道核心对象是什么；
- **顺序错误**：文章在定义之前引入类比、角色或限制；
- **台阶缺失**：从配置直接跳到运行结果，中间没有启动或调用路径；
- **例子失效**：例子需要额外背景，无法凸显目标边界；
- **范围失控**：文章同时解释框架、完整应用和后续主题；
- **证据外包**：关键解释只存在于外部教程；
- **图片错误**：图的包含关系或时序改变了真实架构。

若问题位于文章心智模型或前两节，重写整个解释顺序，而不是只润色作者点名的句子。修改后重新执行独立复读、验证和对应审核模式。

## 十二、完成标准

一篇 Blog 只有同时满足以下条件才算完成：

- 当前 Article Contract 与正文一致；
- 首屏给出中心问题的直接答案；
- 第一次接触主题的读者无需打开外链即可走完主线；
- 正文没有混入给作者的回复、写作取舍、审核过程或发布状态；
- 每个需要外部验证的关键主张都有适合其主题的一手证据；
- 示例、术语、图片和双语版本没有边界冲突；
- 另一 Agent 的最终复读结论为“无阻断问题，内部复读通过”；
- 作者指定的草稿审核或线上审核已经完成；
- 若已发布，Pages、CI、线上页面和 Article Contract 均已核验；存在 tracking Issue 时同步更新。

作者未明确确认的文章保持“等待作者审核”；存在 tracking Issue 时，不得自行关闭。
