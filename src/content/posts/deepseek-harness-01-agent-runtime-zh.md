**从一次失败测试开始，看清模型之外的运行系统。**

TLDR：Agent Loop 解释的是模型为什么会继续调用工具，却没有解释模型这一轮能看到什么、工具请求怎样变成真实操作、任务进度怎样保留下来，以及危险动作为什么会被拒绝。负责这些工作的运行系统就是 Harness。DeepSeek Harness 值得研究的地方，是它把其中不少部分拆开，让它们可以单独接入和替换，同时也把依赖、调试和安全问题带到了台前。

> 版本说明：本文依据 DeepSeek Harness commit [`47f94385`](https://github.com/deepseek-ai/deepseek-harness/commit/47f943859bef60e4160492346772ded9b24f765a) 核验，时间为 2026 年 8 月 16 日。该版本对应 `dsh@0.1.0-rc.5`，项目仍处于开发者预览阶段，后续设计可能变化。

## 1. Agent Loop 解释了什么，又漏掉了什么

假设你把下面这句话交给一个 Coding Agent：

```text
这个测试在重构后失败了。定位原因，修好，再运行相关测试。
```

接下来发生的事情，我们已经很熟悉。Agent 先查看失败信息，搜索可能相关的文件，读取代码，提出修改，再运行测试。测试仍然失败，它读取新的输出，修正判断，继续下一轮。把过程压缩一下，就是常见的 Agent Loop：

```text
模型 -> 选择动作 -> 调用工具 -> 读取结果 -> 再次请求模型
```

这张图没有错。它抓住了 Coding Agent 与普通聊天模型最明显的区别：模型不必在一次回答里猜完所有事情，它可以行动，再根据真实结果修正自己。

问题在于，它解释得太少。

测试失败时，模型需要看到项目说明、相关代码、之前的对话和可用工具。谁把这些内容放进本轮请求？模型决定读取某个文件时，它产生的只是一段结构化请求，谁把请求交给文件系统，又把读取结果送回来？修改已经完成、测试还没运行时，如果任务被中断，哪些进度能够留下？假如模型误判路径，准备修改工作区之外的文件，谁有权阻止它？

这些都不属于“模型下一步选择什么”这个问题。它们也不会因为循环多跑几次就自动解决。

把模型调用工具写成一行箭头，很容易让人产生一个错觉：似乎模型直接拥有文件、Shell 和网络。实际上，模型只能输出意图。一个工具请求能否被识别，是否允许执行，在哪个环境里执行，执行结果怎样记录，都由模型之外的系统决定。

如果你用过 Codex 或 Claude Code，这些责任其实一直在产品体验里。你会看到项目指令影响回答，会看到命令输出进入下一轮，会遇到权限询问，也可以在任务中途补充要求。这些现象说明 Coding Agent 周围存在一套持续工作的运行系统。不同产品怎样实现、开放哪些扩展位置，可以慢慢比较；本篇先把这套系统的范围说清楚。

Agent Loop 回答“动作怎样反复发生”。它没有回答下面四个问题：

1. 模型这一轮能看到什么？
2. 模型提出的工具请求怎样变成真实操作？
3. 任务进度怎样跨过一次模型调用继续保留？
4. 系统怎样限制危险操作？

这四个问题合在一起，才接近一项 Coding Agent 任务实际运行时的样子。

## 2. Harness 还要负责哪些事情

我在本文里用 Harness 指代模型周围的整套运行系统。它负责准备模型行动所需的信息，把模型意图接到真实环境，记录已经发生的事实，并在动作越过边界前做出限制。把它缩成某个单独模块或一份工具清单，都会漏掉大半工作。

这一定义里有一个容易忽略的顺序：Harness 先决定模型能看到什么，模型才能作出下一步判断；模型给出工具请求之后，Harness 还要再次介入，判断这次请求怎样执行。模型位于循环中心，输入却由运行时共同准备，动作权限也掌握在运行时手里。

因此，Harness 至少要完成四类工作。

第一类是上下文准备。系统要从项目指令、对话历史、任务状态和当前可用工具中，选出这一轮模型真正会收到的内容。上下文窗口有限，历史也不等于把所有旧消息原样拼回去。哪些内容保留、哪些工具可见、压缩后的信息怎样替代旧记录，都会改变模型的判断条件。

第二类是工具执行。模型看到的是工具名称、参数格式和用途说明。真正的文件读取、代码修改与命令运行发生在宿主环境中。运行系统要解析请求、找到对应实现、处理取消与超时，再把成功、失败或拒绝整理成模型能继续使用的结果。

第三类是任务状态。一次模型请求结束，不代表任务结束。用户消息、模型输出、工具调用、工具结果和中断原因都可能影响后续工作。系统需要保存已经发生的事实，使下一步、恢复后的任务和派生出来的工作能够从同一份记录开始。

第四类是安全限制。模型可以建议动作，但不能自己授予权限。运行系统要区分普通工作区操作与越界操作，决定是否需要询问用户，并用真正的执行边界限制进程能触及的资源。提示模型“小心一点”不能替代这一层。

下面这张图只表示职责关系，不表示真实进程、网络连接或部署结构。某个产品可以把界面、模型请求、状态存储和执行器放在不同位置，但四个问题仍然存在。

![DeepSeek Harness 的逻辑边界：Agent Loop 位于上下文准备、安全限制、工具执行和任务状态之间](/assets/img/blog/deepseek-harness-01-agent-runtime/harness-boundary.png)

看这张图时不必数方框，先找两条回路。第一条是大家熟悉的模型与工具回路：模型提出请求，系统执行，结果返回。第二条更少出现在简化示意图里：消息、步骤和工具结果进入任务状态，再由这些状态重建下一轮上下文。缺少第二条回路，Agent 仍然可以调用工具，却很难稳定地继续一项长任务。

Harness 的边界也不等于整个产品。用户界面在边界之外，模型服务、文件系统和外部服务也在边界之外。Harness 负责连接这些对象，并保证每次连接都服从同一套状态和权限规则。把所有东西都塞进 Harness 这个词，只会让它失去解释力。

到这里，通用框架已经够用了。接下来不再抽象地罗列“上下文层、工具层、状态层”。我们直接看 DeepSeek Harness 怎样回答开头的四个问题。

## 3. DeepSeek Harness 怎样组织这些工作

DeepSeek Harness 官方把自己的架构概括为 “everything is a plugin”。这句话很容易被理解成“工具都可以做成插件”，但官方架构文档给出的范围更大：模型接入、工具注册、任务记录和 Agent Loop 本身都能以插件方式接入运行时。

第 2 篇会专门解释插件系统和负责插件运行的 Cordis。这里先不追它们的加载方式，只看这种设计怎样落到一次任务中。

### 模型这一轮能看到什么

回到失败测试。模型开始分析之前，至少需要用户要求、项目约束、相关历史和一组可用工具。模型并不知道这些信息存放在哪里，也不会自己从磁盘上捞出系统指令。它收到的是运行系统为这一轮组装好的请求。

DeepSeek Harness 会在每一步模型请求前组装系统提示词和工具定义。不同插件可以贡献提示词片段、附加上下文或工具说明；当前 Agent 的范围又会限制哪些注册项真正可见。输入进入下一步之前，运行时还有机会改写或拒绝它。

这带来一个很实用的判断：上下文是每一轮重新计算出来的结果，一段固定的大提示词解释不了它。项目说明变了、工具集合变了、任务恢复了，下一次请求看到的内容也可以跟着变化。模型能力没有改变，判断条件却已经改变。

失败测试案例中，如果 Agent 不知道项目要求先运行哪条检查命令，问题未必是模型不会调试，也可能是要求没有进入这一轮上下文。如果一个工具已经卸载，却仍然留在模型看到的工具列表里，说明 Harness 没有让“可见能力”和“真实能力”保持一致。

DeepSeek Harness 还把本轮使用的系统提示词与工具定义写进任务记录。这样，任务中断后重新开始时，系统不需要猜当时给过模型什么。每次模型请求都能从已有记录重建。这是可审计性的基础，也避免界面里看到的聊天记录与模型实际收到的内容变成两套互相矛盾的历史。

### 工具请求怎样变成真实操作

模型决定读取文件时，只会输出一次工具调用，拿不到文件内容。这次调用通常包含工具名称和参数。到这里，模型的工作暂时结束，Harness 的执行流程开始。

DeepSeek Harness 先把调用写入任务记录，再交给统一的工具执行流程。系统会确认工具存在、参数可以解析，并在实际运行之前完成权限检查。只有允许执行的请求才会进入工具本体。完成后，结果还要经过整理，变成唯一一份可以写入任务记录、显示给界面并反馈给模型的结果。

这个过程看起来比“调用一个函数”复杂，但复杂度有明确用途。模型历史里的调用、界面展示的调用和宿主真正执行的调用必须是同一件事。如果某个中间步骤可以悄悄改掉参数，审计记录说它读取了 `src/`，真实执行却访问了另一个目录，后续所有安全判断都会失去意义。

失败本身也要进入循环。文件不存在、测试返回非零状态、审批被拒绝，这些运行时细节都不能藏起来。它们是下一轮判断所需的事实。Agent 只有看见真实结果，才能换一条路径，不能假定动作已经成功。

“模型会用工具”只解决了一半问题。模型要能选择合适动作，系统也要让路由、取消、策略、结果格式和状态记录彼此配合。Agent Loop 画出了两者之间的箭头，Harness 负责让这条箭头真的成立。

### 任务进度怎样保留下来

假设 Agent 已经定位问题并修改文件，正准备运行测试，任务却被中断。重新打开时，系统不能只保留最后一句模型回复。它至少要知道用户提出过什么要求、模型做过哪些判断、哪些工具调用已经发生、文件修改是否成功，以及中断发生在什么位置。

DeepSeek Harness 把这些事实写进一种只追加的任务记录，官方称它为 Session。用户消息、模型输出、工具调用和工具结果按照发生顺序加入，下一次模型请求需要的历史也从这里重建。任务中断后，系统可以据此判断已经做完什么、下一步还缺什么。

聊天界面里的消息列表只是 Session 的一种展示。Session 还要保存运行事实。一次工具调用在界面上可能只是一张“运行测试”的卡片，对运行时来说，还要知道它有没有完成、返回了什么结果。

在失败测试案例里，这条记录让“已经修改，尚未验证”成为可以恢复的进度，比一句模糊的自然语言备注具体得多。任务怎样分轮次推进、怎样恢复，以及怎样从已有进度分出新任务，留到第 3 篇再谈。本篇只需要确认：保存运行事实是 Harness 必须承担的一项责任。

### 谁来限制危险操作

模型提出动作，不等于系统允许动作。对 Coding Agent 来说，这个区别直接关系到安全，因为“工具调用”背后可能是读取普通源码，也可能是修改工作区之外的文件、执行删除命令或启动一个能继续访问宿主资源的进程。

DeepSeek Harness 会在工具真正执行前，同时考虑这次操作是否需要用户确认，以及执行环境实际上允许它触及哪些文件。前一个问题由审批处理，后一个问题依靠沙箱等执行边界。两者不能互相替代：不需要询问用户，不等于进程可以越过既定边界。

系统还要保证多项安全检查不会互相撤销：一项检查已经拒绝的调用，后面的环节不能再把它改成允许。至于审批如何触发、沙箱怎样实现，以及不同资源各自需要什么限制，留到第 5 篇展开。

回到失败测试。如果 Agent 只修改工作区中的目标文件，操作可以在既定范围内继续。如果它试图写到工作区之外，系统可以要求审批或直接拒绝。拒绝结果随后回到 Session，Agent 应该调整方案，不能靠换一种命令拼写绕过边界。

安全机制不会让模型不犯错。它负责把模型错误与真实系统权限隔开，并让拒绝也成为下一轮可以理解的结果。安全边界要落在 Harness 中，写进系统提示词的一句行为建议远远不够。

把四个问题连起来看，DeepSeek Harness 的组织方式就清楚了。系统在每一步之前组装上下文，Agent Loop 请求模型，工具流程把模型意图接到真实环境，Session 保存发生过的事实，安全限制决定哪些动作能够落地。它们共同完成一次任务，却不必被写死在同一个实现里。

## 4. 更灵活的运行方式带来了什么代价

把模型接入、工具、任务记录和 Agent Loop 都做成可以接入或替换的部分，最直观的好处是控制力。团队可以换模型提供方，可以为不同任务提供不同工具，也可以让文件系统与 Shell 指向隔离环境，而不必重写整条执行流程。

不过，“可以替换”只是一项能力声明。替换之后，系统还能维持原来的约束，这项能力才有价值。

以文件执行环境为例。如果文件工具已经指向远程沙箱，Shell 仍然在本地运行，Agent 看到的就会是两个不同世界。它读取的是远程文件，测试的却可能是本地代码。好的替换边界不只需要接口形状一致，还要保证相关能力面对的是同一套文件和运行环境。

卸载也一样。一个插件可能注册了工具、监听事件、启动后台任务，还依赖另一个服务。它离开时，如果只有工具名称消失，监听器和任务仍在运行，系统状态会逐渐变得不可解释。反过来，如果它依赖的服务被替换，系统也要决定当前插件是重新启动、暂时停用，还是继续持有已经过期的对象。

这些问题会直接增加调试成本。一次失败可能来自模型判断，也可能来自上下文组装、插件加载顺序、工具提供方、权限策略或持久化后端。边界更清楚，有助于定位问题；边界更多，也意味着要观察更多位置。两件事可以同时成立。

兼容性压力同样真实。DeepSeek Harness 目前仍处于开发者预览阶段，官方明确提醒会出现破坏兼容性的变化。当 Agent Loop 和任务记录也可以被替换时，插件之间共享的事件顺序、取消方式和记录格式就不能只靠约定俗成。一个实现可以换掉，不代表它可以破坏其他部分依赖的系统规则。

安全代价也很具体：开放的替换位置越接近运行时核心，插件获得的权力越大。替换工具执行策略或任务记录的保存方式，拥有的权限和风险面远高于增加一个只读搜索工具。系统需要让扩展足够灵活，同时明确哪些规则不能被后来的组件放宽。

因此，我不认为 DeepSeek Harness 的价值可以用“插件多”来概括。它把许多原本容易写死在 Agent 主循环周围的责任，变成可以单独组合的部分。这样做换来了实验和定制空间，也要求系统认真处理卸载、依赖、兼容性、调试与权限。

Codex 和 Claude Code 同样需要准备上下文、执行工具、保存进度并限制操作。差别不在于谁“有 Harness”，而在于哪些边界是产品内部固定的，哪些边界公开给配置或扩展系统。本篇不做强弱排名，因为只有在相同版本、相同问题和相同观察尺度下，比较才有意义。

## 5. 为什么下一篇要谈插件系统

现在我们已经知道，Agent Loop 只是整套运行系统中的一部分。DeepSeek Harness 进一步把上下文、工具、状态和执行策略拆开，让它们能够参与同一项任务，又可以分别接入和替换。

新的问题随之出现：一个插件注册的工具和监听器，卸载时怎样完整消失？它依赖的服务被替换时，谁负责让它停止、重新连接或重新启动？多个插件都想影响同一次工具执行，系统怎样保证顺序明确，而且安全拒绝不会被后面的组件推翻？

这些已经不是 Agent Loop 能回答的问题。它们属于插件的依赖与生命周期。

下一篇讨论：[DeepSeek Harness 为什么要用插件系统？](https://github.com/LuNa-shi/luna-shi.github.io/issues/3) 我们会进入 Cordis，但仍然从工程问题出发：插件容易加载，难的是让它在该离开时完整离开，并在依赖变化时保持正确。
